# DIGITAL HEROES — CODE QUALITY & NO ARTIFICIAL ARTIFACTS STANDARD

## PURPOSE

Produce clean, natural, production-quality code.

The codebase must read like a deliberately engineered professional
software project.

Do not add unnecessary AI/meta artifacts to source code.

---

# 1. NO AI META CONTENT

Never add comments, strings, headers, or documentation such as:

- "Generated by AI"
- "AI-generated code"
- "Generated by ChatGPT"
- "Generated by Claude"
- "Generated by Gemini"
- "As an AI..."
- "AI assistant"
- "LLM-generated"
- "This code was generated..."
- "The AI decided..."
- "Prompt:"
- "Generated response:"
- "AI TODO"

Do not mention the coding agent inside application source code.

---

# 2. NO META EXPLANATIONS IN SOURCE

Do not add comments explaining that the code was created,
generated, optimized, or suggested by an AI.

Comments must describe the software itself.

Good:

// Preserve the previous prize allocation for audit history.

Bad:

// AI-generated implementation for prize allocation.

---

# 3. COMMENTS MUST BE PURPOSEFUL

Do not comment every line.

Comments should explain:

- WHY a non-obvious decision exists
- important business constraints
- security requirements
- unusual edge cases
- architectural boundaries
- external integration behavior

Do not write comments that merely restate obvious code.

Bad:

const user = getUser(); // Get the user

Good:

// The subscription webhook is the authoritative source for lifecycle
// changes; browser checkout state is not trusted.

---

# 4. NATURAL NAMING

Use precise, domain-driven names.

Prefer:

calculatePrizePool()
validateGolfScore()
publishDraw()
verifyWinnerProof()

Avoid artificial names such as:

doThing()
processData()
handleEverything()
magicFunction()
aiHelper()
smartLogic()
generatedService()

Names should communicate the real responsibility.

---

# 5. NO ARTIFICIAL VERBOSITY

Do not make files unnecessarily large merely to appear sophisticated.

Avoid:

- excessive abstractions
- unnecessary wrapper functions
- pointless interfaces
- duplicate utilities
- redundant comments
- fake enterprise patterns
- unnecessary design patterns

Use the simplest architecture that satisfies the engineering requirements.

---

# 6. NO PLACEHOLDER PRODUCTION CODE

Do not leave source-code markers such as:

TODO: implement later
FIXME: AI-generated
HACK: temporary AI solution
PLACEHOLDER: generated implementation

If something genuinely remains unfinished:

- document it in the appropriate planning/risk document
- do not pretend it is complete

---

# 7. NO FAKE IMPLEMENTATION

Never create an implementation merely to make a feature appear complete.

Do not use:

- hard-coded fake success
- fake payment completion
- fake winner status
- fake subscription state
- fake prize values
- fake database results

Production UI must reflect real backend/application state.

---

# 8. CONSISTENT ENGINEERING STYLE

Follow the existing project's conventions.

Before adding code:

- inspect nearby files
- inspect naming conventions
- inspect import style
- inspect component patterns
- inspect error handling
- inspect testing patterns

Extend the existing system consistently.

Do not introduce a completely different coding style without a reason.

---

# 9. DOCUMENTATION SEPARATION

Keep planning and reasoning outside application source where appropriate.

Use:

docs/

for:

- architecture decisions
- assumptions
- risk analysis
- implementation plans
- technical reasoning
- evaluation mapping

Keep application source focused on application behavior.

---

# 10. ERROR MESSAGES

User-facing messages must be product-oriented.

Do not expose internal implementation or agent terminology.

Bad:

"AI generated request failed."

Good:

"Unable to complete the request. Please try again."

Developer logs may contain technical context, but never AI metadata.

---

# 11. TEST CODE

Tests must look like real tests.

Use descriptive names based on behavior.

Good:

should_reject_duplicate_score_for_same_user_and_date()

Bad:

ai_test_1()
generated_test_case()
testByAI()

Tests should describe business behavior.

---

# 12. GIT / PROJECT ARTIFACT HYGIENE

Do not add:

- AI notes
- prompt transcripts
- agent conversations
- temporary generated files
- scratch files
- debugging dumps

to the production source tree.

Keep temporary experimentation outside the final project structure.

---

# 13. NO UNNECESSARY SELF-DOCUMENTATION

Do not add comments such as:

"Here is what I am doing."

"Step 1..."

"AI reasoning..."

"Implementation generated..."

"Following the prompt..."

The source should describe the software, not the development conversation.

---

# 14. CODE REVIEW STANDARD

Before considering a feature complete, inspect the changed files for:

- AI/meta references
- unnecessary comments
- placeholder markers
- fake implementations
- inconsistent naming
- duplicated logic
- unnecessary abstractions
- temporary debugging
- accidental secrets
- unnatural code structure

Remove anything that does not belong in production.

---

# 15. FINAL RULE

Write code that is:

- clear
- intentional
- domain-driven
- maintainable
- concise where appropriate
- properly documented
- testable
- secure

The source code should communicate the quality of the engineering,
not the process used to produce it.
