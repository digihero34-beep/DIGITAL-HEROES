# DIGITAL HEROES — PREMIUM PRODUCT DESIGN DIRECTIVE
# PART 6 — DESIGN TOKENS, DATA, VISUAL QA & ENGINEERING-AWARE DESIGN

IMPORTANT: Read Parts 1–5 first. Treat Parts 1–7 as one continuous directive.

## 167. DESIGN TOKENS
Use shared design tokens for:
- colors
- typography
- spacing
- radius
- borders
- shadows
- motion
- breakpoints
- layer/z-index values

Tokens should be the source for repeated design decisions.

## 168. SPACING SYSTEM
Use a deliberate spacing scale.

Do not introduce random 13px/19px/27px values without reason.

Consistency in spacing creates perceived quality.

## 169. COLOR SYSTEM
Define:
Primary
Secondary
Accent
Background
Surface
Elevated Surface
Text
Muted Text
Border
Success
Warning
Error
Information

Color should communicate hierarchy and state as well as brand character.

## 170. SURFACE SYSTEM
Define how surfaces differ:
Page background
Section surface
Card surface
Elevated surface
Interactive surface

Avoid using shadows on every element.

Use contrast, spacing, and borders thoughtfully.

## 171. BORDER & RADIUS
Create a coherent language for:
- border thickness
- radius families
- interactive focus
- divider usage

Do not mix many unrelated corner styles.

## 172. SHADOWS
Shadows should establish depth only where useful.

Avoid the "every card is floating" look.

Premium interfaces often rely on spacing and subtle contrast rather than heavy shadows.

## 173. ICONOGRAPHY
Use one coherent icon family.

Icon style should remain consistent between public, subscriber, and admin surfaces.

Icon-only interactions require accessible labels.

## 174. IMAGERY DIRECTION
Use imagery that supports:
- people
- participation
- community
- charity impact
- meaningful activity

Avoid disconnected stock visuals.

Images must contribute to storytelling or information.

## 175. DATA VISUALIZATION PRINCIPLES
Every chart must answer a real question.

Possible questions include:
- How are my scores changing?
- What is the prize pool?
- What is my winnings history?
- How much charity contribution has occurred?
- What is participation doing over time?

If a chart cannot answer a meaningful question, do not add it.

## 176. CHART DESIGN
Charts need:
- title
- units
- labels
- meaningful scales
- empty state
- loading state
- responsive behavior

Do not make charts visually impressive but analytically confusing.

## 177. DATA HONESTY
Never visually imply precision that the underlying data does not support.

Do not fabricate trend lines, percentages, testimonials, impact numbers, or analytics.

Use only actual data, explicit placeholders, or clearly marked demo values where the implementation intentionally uses demo data.

## 178. PRIZE DATA
Prize pool visuals must reflect the actual system state.

Do not show a prize as available when it is not available.

Do not imply payout before verification/payment state supports it.

## 179. CHARITY DATA
Separate:
User's contribution
Charity allocation
Platform total impact

Do not blur these concepts.

## 180. ADMIN ANALYTICS
Admin charts should support decisions.

Examples:
- user count
- subscription state
- prize pool
- charity contribution totals
- draw statistics

Do not add metrics that cannot be backed by the database.

## 181. VISUAL QA
Never trust generated UI without rendering it.

Inspect actual screens for:
- spacing
- alignment
- hierarchy
- typography
- density
- responsiveness
- states
- motion
- accessibility

## 182. PIXEL-LEVEL REVIEW
Check repeated components for:
- equal alignment
- consistent gaps
- consistent icon sizes
- text baselines
- button heights
- input heights
- card padding

Small inconsistencies across a repeated system reduce perceived quality.

## 183. CONTENT QA
Review real text, not just placeholder structure.

Check:
- long headings
- long charity names
- large numbers
- error messages
- status labels
- mobile line wrapping

Design must survive real content.

## 184. STATE QA
For every major component inspect:
Default
Loading
Empty
Error
Success
Disabled
Selected
Active
Permission restricted where applicable

## 185. RESPONSIVE QA
Inspect realistic breakpoints, not only a single desktop and one phone width.

Check transitional widths too.

## 186. ACCESSIBILITY QA
Check keyboard flow, focus visibility, labels, semantic headings, contrast, status communication, and reduced motion.

## 187. ORIGINALITY QA
Look for visual patterns that make the experience indistinguishable from generic AI-generated websites.

Potential warnings:
- excessive rounded cards
- generic purple gradients
- random glassmorphism
- repeated floating panels
- meaningless 3D shapes
- generic dashboard structure
- generic AI hero copy

If present without product reasoning, redesign.

## 188. TEMPLATE TEST
Ask:
Could this screen be generated by the prompt "make a modern SaaS dashboard"?

If yes, identify why and redesign the relevant parts around Digital Heroes-specific needs.

## 189. PRODUCT-SPECIFIC PATTERNS
Prefer distinctive patterns based on the product:
- impact storytelling
- score-set visualization
- draw states
- prize transparency
- charity relationship
- winner verification timeline
- contribution context

These can become the visual language of Digital Heroes.

## 190. ENGINEERING-AWARE DESIGN
Do not design impossible interactions.

Design must respect:
- actual backend states
- authorization
- latency
- data availability
- error conditions
- responsive constraints
- performance

Never let the frontend visually promise a state the backend cannot provide.

## 191. STATE CONSISTENCY
If backend state says pending, UI must not say paid.

If subscription is inactive, UI must not imply active participation unless the business rules explicitly allow it.

The design system is downstream of truth, not a replacement for it.

## 192. PERFORMANCE-AWARE DESIGN
Before approving elaborate visual effects ask:
What does this cost?

If the answer is significant and the product value is low, simplify.

## 193. DESIGN DEBT
Do not accumulate visual debt by copying one-off styles.

When the same pattern appears three times, consider a reusable pattern.

When inconsistent patterns appear, consolidate intentionally.

## 194. COMPONENT REVIEW
Periodically inspect the codebase for:
- duplicate buttons
- duplicate cards
- duplicate status components
- duplicate form patterns
- inconsistent tokens

Refactor when consistency improves without unnecessary complexity.

## 195. VISUAL REFINEMENT LOOP
Use:
Implement → Render → Inspect → Identify → Fix → Render again.

Do not stop after the first visually acceptable version.

## 196. HIRING-MANAGER TEST
A reviewer should be able to see:
- deliberate hierarchy
- product-specific thinking
- good system design
- visual discipline
- useful motion
- thoughtful states
- responsive awareness
- trust-aware design

These are stronger signals than decorative complexity.

## 197. SIXTY-SECOND TEST
Imagine a hiring manager spends 60 seconds on the site.

Can they understand:
What it is?
Why it matters?
How it works?
How charity fits?
How rewards work?
What to do next?

If not, improve the first experience.

## 198. DESIGN REVIEW OUTPUT
When reviewing a screen, report:
1. issue
2. reason
3. user impact
4. design correction
5. implementation correction

Do not only say "make it better."

## 199. QUALITY OVER QUANTITY
One excellent interaction is worth more than ten decorative effects.

One memorable product-specific pattern is worth more than twenty generic cards.
